# Teaching a Language Model to Query a Cricket Knowledge Graph with Reinforcement Learning

*A living blog — updated as the project progresses. Started 2026-03-16.*

---

## What We're Building

The question sounds simple: *Who scored the most runs in IPL 2019?*

Any cricket fan can answer it. But can a language model figure it out by itself — by writing a database query, reading the results, and reasoning toward an answer — without being told the answer in advance?

That's the core of this project. We have a Neo4j knowledge graph containing ball-by-ball IPL T20 data: every match, every innings, every delivery, every player performance across multiple seasons. The model gets access to three tools: one to inspect the schema, one to run Cypher queries against the graph, and one to submit a final answer. It has to figure out the rest on its own.

The model we're training is **Qwen3-30B-A3B** — a 30 billion parameter mixture-of-experts model from Alibaba. We're fine-tuning it with **RL (reinforcement learning)** using the **Tinker** platform from Thinking Machines Lab, who have been generous in providing compute credits for this experiment. The training loop runs on a CPU machine; Tinker handles the GPU-heavy forward passes and gradient updates on their servers.

The goal isn't just a model that answers cricket questions. It's a proof of concept for a broader pattern: an RL agent that learns to query a domain-specific knowledge graph by trial and error, with the knowledge graph as its only source of ground truth.

---

## The Stack

Before we get to the interesting failures, here's what the system looks like:

**Knowledge graph:** Neo4j AuraDB (cloud-hosted), populated with IPL T20 data. Node labels include `Player`, `Team`, `Match`, `Innings`, `BattingPerformance`, `BowlingPerformance`, `Delivery`, `Wicket` and more. The schema has ~24 relationship types connecting them.

**Agent tools:**
- `get_schema()` — returns all node labels, relationship types, properties, constraints, and indexes
- `run_cypher(query)` — executes a read-only Cypher query, returns up to 20 rows as JSON
- `final_answer(answer)` — submits the answer, ends the episode, triggers the reward function

**Training loop:** Each episode is one question. The model calls tools until it either submits a final answer or hits the turn limit (8 turns). The reward function scores the answer against a known ground truth. Gradients flow back through the token sequences using DAPO (a variant of PPO/GRPO that handles the case where all trajectories in a group have the same reward).

**Question dataset:** 100 questions auto-generated by querying Neo4j directly. Templates cover season-level stats (top run scorer, wicket taker, sixes, economy rate, etc.) and career stats for the top 20 players. Each question has a known correct answer used only by the reward function — never shown to the model.

## Part 1: Getting the Schema Right

The first challenge wasn't training at all — it was making sure the model could see the graph structure accurately.

We initially used `db.schema.nodeTypeProperties()` — a built-in Neo4j procedure that returns property names per node label. It seemed like the right call. But it silently returned nothing for most node labels, because it only returns properties that have constraints or indexes defined. Most of our properties had neither.

The fix: sample actual data nodes to discover all properties in use.

```python
# Wrong: only returns constrained/indexed properties
CALL db.schema.nodeTypeProperties() YIELD nodeType, propertyName

# Right: sample from actual data
MATCH (n:BattingPerformance) WITH n LIMIT 1
RETURN keys(n) AS properties
```

A second bug: we were formatting property lists with square brackets — `[runsScored, ballsFaced, ...]` — and passing them to a Rich console for display. Rich uses square brackets as markup tags (for styling). It silently consumed everything inside the brackets and displayed nothing. The fix was to just remove the square brackets from the format string.

A third bug: the `SHOW INDEXES` and `SHOW CONSTRAINTS` commands in Neo4j have a specific clause ordering requirement that's easy to get wrong:

```cypher
-- Wrong
SHOW INDEXES WHERE type <> 'LOOKUP' YIELD name, type

-- Right
SHOW INDEXES YIELD name, type, labelsOrTypes, properties WHERE type <> 'LOOKUP'
```

None of these are deep ML problems. They're the kind of silent failures that can corrupt your entire training signal without a single error being thrown.

After fixing all three, the schema shown to the model looked like this:

```
=== NODE LABELS AND PROPERTIES ===
  :`BattingPerformance`  properties: performanceId, runsScored, ballsFaced, fours, strikeRate, isOut, sixes
  :`BowlingPerformance`  properties: performanceId, economy, wicketsTaken, dotBalls, oversBowled, runsConceded
  ...

=== RELATIONSHIP TYPES (fromLabel)-[:TYPE]->(toLabel) ===
  (:Player)-[:BATTING_PERFORMANCE]->(:BattingPerformance)
  (:BattingPerformance)-[:PERFORMANCE_IN_INNINGS]->(:Innings)
  (:Match)-[:HAS_INNINGS]->(:Innings)
  ...
```

The relationship endpoints — `(fromLabel)-[:TYPE]->(toLabel)` — turned out to be critical. Without them, the model had no idea which direction to traverse relationships or which nodes connected to which. Adding them immediately improved the quality of Cypher queries in early testing.

## Part 2: The Reward Function — Getting It Wrong First

The reward function is the signal the model learns from. If you get it wrong, the model learns the wrong thing. We got it wrong first.

### The Wrong Reward: 0.3 for Just Showing Up

Our first reward function was designed with good intentions. We wanted to reward the model for:
1. Actually calling `final_answer` (format compliance) — **0.3 points**
2. Getting the entity right (e.g., "DA Warner") — **+0.3 points**
3. Getting the number right (e.g., "692 runs") — **+0.4 points**

This decomposition was inspired by ToolRL (NeurIPS 2025), which argues that fine-grained reward decomposition gives denser gradient signal than binary 0/1 rewards. That part is correct. The mistake was the 0.3 base reward for format.

Here's what the first 5-step smoke run looked like:

| Step | Reward | Turns/episode |
|------|--------|---------------|
| 0    | 0.19   | 5.5           |
| 1    | 0.32   | 3.5           |
| 2    | 0.28   | 3.1           |
| 3    | 0.31   | 3.0           |
| 4    | 0.32   | 3.1           |

Reward going up, turns going down. Looks like learning! We launched a full 50-step run with confidence.

### The Collapse

Here's the full run:

| Steps | Turns/ep | Reward | What's happening |
|-------|----------|--------|-----------------|
| 0–4   | 5→3      | 0.19–0.39 | Model queries DB, some entity matches |
| 5–14  | ~3       | 0.06–0.4  | Variable, still querying |
| 15–18 | 3→2.5    | 0.30      | Suspicious |
| 19–24 | **1.0**  | **0.30**  | **Full collapse** |

By step 19, every single episode was one turn long. The model would receive the question, immediately call `final_answer("I don't know")`, and collect its guaranteed 0.3 reward. No schema lookup. No Cypher query. Pure reward hacking.

The model had discovered the optimal policy under our reward function: skip all the hard work, call `final_answer` with any guess, collect 0.3. Querying the database is risky — it might still get entity or number wrong and end up at 0.3 anyway after spending 3 turns. Better to guarantee 0.3 in 1 turn.

This is why `frac_all_bad = 1.0` appeared in the metrics. In DAPO, advantages are centered within each group of rollouts for the same question. If every trajectory in a group gets reward 0.3, the advantages are all zero. The gradient update is zero. The model is frozen in its degenerate state.

**The 5-step smoke run was too short to reveal this.** The hacking took ~15 gradient updates to manifest. We declared victory at step 5.

### The Right Reward: Gate on DB Usage

The fix is simple in hindsight: if the model didn't query the database, reward = 0. No exceptions.

```python
def compute_reward(final_answer, ground_truth, used_db):
    if not used_db:
        return 0.0, {"reward/no_db_query": 1.0}
    if final_answer is None:
        return 0.0, {"reward/no_answer": 1.0}

    entity_match = gt_entity in normalise(final_answer)
    number_match = gt_number == extract_number(normalise(final_answer))

    reward = (0.4 if entity_match else 0.0) + (0.6 if number_match else 0.0)
    return reward, {"reward/entity_match": float(entity_match), ...}
```

`used_db` is determined by scanning the message history for any `run_cypher` tool call. If none exists, the episode gets zero regardless of what `final_answer` said. The model now has to earn its reward.

**Lesson: Never give a base reward for behavior the model can perform trivially.** Format rewards backfire when the format can be satisfied without doing the task.

## Part 3: The Dataset That Ran Out

With the reward fixed, we launched again. This time we ran into a different silent failure: the dataset exhausting before `max_steps` was reached.

We had 100 questions. With `groups_per_batch=4` questions per step, the dataset had exactly 25 unique batches. Our `CricketKGDataset.get_batch(index)` was:

```python
def get_batch(self, index):
    start = index * self.batch_size
    return self.builders[start : start + self.batch_size]  # empty slice after step 25
```

At step 25, `start = 100`, the slice was empty, and training silently stopped. `progress/done_frac` hit 1.0 at step 24 even though we'd asked for 50 steps.

The fix: make `__len__` return a large number (10,000) so the training loop uses `max_steps` to decide when to stop, and make `get_batch` cycle with a per-epoch shuffle:

```python
def get_batch(self, index):
    batches_per_epoch = ceil(len(self.builders) / self.batch_size)
    local_idx = index % batches_per_epoch
    epoch = index // batches_per_epoch
    if epoch != self._epoch:
        self._epoch = epoch
        random.shuffle(self._order)  # reshuffle on new epoch
    start = local_idx * self.batch_size
    return [self.builders[i] for i in self._order[start:start + self.batch_size]]
```

**Lesson: Always verify that training actually runs for `max_steps` steps. Check `progress/done_frac` in the metrics.**

## Part 4: Genuine Learning — and a New Collapse

With both fixes in place, the third run showed something genuinely exciting in the first 14 steps:

| Step | Reward | Entity match | Number match | Turns/ep |
|------|--------|-------------|-------------|----------|
| 0    | +0.60  | 0.92        | 0.62        | 4.25     |
| 2    | +0.53  | 0.69        | 0.62        | 4.12     |
| 6    | +0.31  | 0.71        | 0.71        | 4.31     |
| 9    | **+0.75** | **0.75** | **0.75** | **3.00** |
| 14   | +0.38  | 0.56        | 0.25        | 3.88     |

Step 9: reward 0.75. Both entity and number matching in 75% of trajectories. The model was querying the DB, reading the results, and giving correct answers. Not every time — but genuinely learning.

The conversations log confirmed it. Here's a real episode from step 9:

> **Q:** How many total wickets did DL Chahar take across all IPL seasons in this dataset?
>
> **Model called:** `get_schema()` → `run_cypher("MATCH (p:Player {name: 'DL Chahar'})-[:BOWLING_PERFORMANCE]->(bp:BowlingPerformance) RETURN sum(bp.wicketsTaken)")` → received `61` → `final_answer("DL Chahar took a total of 61 wickets")`
>
> **Ground truth:** 61 wickets in 61 innings
> **Reward:** 1.0 ✓

Then at step 15, everything changed.

### The Format Collapse

`parse_error` appeared in the metrics for the first time at step 15 and never left. By step 18, `no_db_query = 1.0` — all episodes, no DB queries at all.

Reading `conversations.jsonl` revealed what happened. Here's a representative episode from step 20:

```
[USER] How many total wickets did Mohammed Shami take...?
[ASSISTANT] calls get_schema() ✓
[TOOL RESULT] <full schema>
[ASSISTANT TEXT] [{'type': 'text', 'text': '<tool_call>\n{"name": "run_cypher", "arguments":
  {"query": "MATCH (p:Player {playerId:봄})\nWHERE'excluded'!misINCLUDED其中..."}}'
```

The model was generating tool calls as plain text — `<tool_call>JSON</tool_call>` inside a text message instead of as structured tool calls. The framework couldn't parse these. The `-0.1` parse penalty from the framework made total rewards go negative.

And the Cypher inside those malformed tool calls was completely garbled: Korean characters, Chinese characters, Thai characters mixed into what should have been valid Cypher syntax. Classic hallucination under distribution shift.

**What caused it:** `kl_penalty_coef = 0.0`. With no KL regularization, the model was free to drift arbitrarily far from its base distribution. After ~15 gradient updates reinforcing certain generation patterns, the model's weights shifted enough to change how it formatted tool calls — reverting to Qwen3's pretraining format (`<tool_call>` XML in text) instead of the structured tool call format the framework expected. The `qwen3_disable_thinking` renderer suppresses thinking at inference time but can't prevent the model from learning to generate thinking during training.

The KL penalty prevents this by adding a regularization term to the loss:

```
total_loss = policy_loss + kl_coef × KL(π_new || π_ref)
```

When the model's distribution drifts too far from the reference (base) model, the KL term increases the loss, pulling it back. `kl_penalty_coef = 0.05` is our next experiment.

**Lesson: Zero KL penalty is dangerous for models with strong pretraining priors about output format (like Qwen3's thinking + XML tool call style). Start with at least 0.01–0.05.**

## Part 6: Run 6 — The KL Fix Works

The hypothesis going into Run 6 was simple: add `kl_penalty_coef=0.05` and the format collapse won't happen. The result was better than expected.

**Run 6 config:**
- `kl_penalty_coef = 0.05` with `kl_reference_config = KLReferenceConfig(base_model="Qwen/Qwen3-30B-A3B")`
- `load_checkpoint_path = tinker://3685091a.../weights/000010` — starting from Run 5 step 10
- `max_steps = 50`, `save_every = 5`

The KL reference is the original base model. Every gradient update, the training loss includes a penalty proportional to how far the policy has drifted from the base Qwen3-30B-A3B weights. This keeps the model from wandering into a regime where it generates `<tool_call>` XML or thinking tokens.

One implementation detail: Tinker requires an explicit `kl_reference_config` object whenever `kl_penalty_coef > 0`. Simply setting the coefficient isn't enough — you also have to tell it which model to measure KL against. Missing this raises a `ValueError` at training start.

### The Numbers

| Metric | Run 5 (kl=0.0) | Run 6 (kl=0.05) |
|--------|----------------|------------------|
| Total episodes | 634 | 800 |
| Reward > 0 | 125 (19.7%) | **400 (50.0%)** |
| Full credit (1.0) | 66 (10.4%) | **297 (37.1%)** |
| No DB query | 40.2% | **0.0%** |
| Parse errors | Collapsed at step 15 | **0.0% throughout** |

Not a single episode across all 800 went without querying the database. Not one parse error in 50 steps. The KL penalty did exactly what it was supposed to.

### A Working Example

After training, a smoke test on the Run 6 step 30 checkpoint:

> **Q:** How many total wickets did Rashid Khan take across all IPL seasons in this dataset?
>
> **Model called:** `get_schema()` → `run_cypher("MATCH (p:Player {name: 'Rashid Khan'})-[:BOWLING_PERFORMANCE]->(bp:BowlingPerformance) RETURN SUM(bp.wicketsTaken) AS totalWickets")` → received `107` → `final_answer("Rashid Khan took a total of 107 wickets across all IPL seasons in this dataset.")`
>
> **Verified against Neo4j directly:** 107 ✓

3 turns. Correct schema traversal. Correct Cypher. Correct answer.

### The Remaining Gap

Season-specific questions are still unreliable. When asked *"who scored the most runs in IPL 2018?"*, the model wrote:

```cypher
MATCH (p:Player)-[:BATTING_PERFORMANCE]->(bp:BattingPerformance)
RETURN p.name, SUM(bp.runsScored) ORDER BY total_runs DESC LIMIT 1
```

That returns career totals (S Dhawan, 3004 runs — his entire career, not 2018 alone). The correct query needs to join through `BattingPerformance → Innings → Match` and filter by `Match.season = 2018`. The model has seen this schema — it retrieves it correctly every time — but hasn't yet reliably learned to apply the season-filter join pattern.

This is the next learning target: more gradient updates on season-specific questions, giving the model enough signal to internalize the `Innings → Match → season` traversal.

## Part 7: Run 7 — A New Collapse We Didn't Expect

The hypothesis for Run 7 was simple: load from Run 6 step 30, run 100 steps, give the model more time to learn the season-filter pattern. We were wrong about how simple it would be.

Run 7 collapsed at step 13. But it wasn't the same collapse as before.

### A Different Failure Mode

In Run 5, the model lost its tool call format — it started generating `<tool_call>` XML as plain text. In Run 7, the format was fine. The model was still making structured tool calls. But it stopped querying the database entirely.

`conversations.jsonl` showed the same pattern across hundreds of episodes: two turns, empty assistant messages, `final_answer = None`. The model was generating text — but the text was invisible.

The culprit: **thinking tokens.**

Here's what was actually happening. After receiving the question, the model was generating `<think>...</think>` content — extended internal reasoning. The `qwen3_disable_thinking` renderer strips all of this from the visible output, leaving an empty assistant message. The framework sees no tool call, ends the episode, reward = 0.

### Why qwen3_disable_thinking Isn't a Hard Block

This required digging into the renderer source code to understand. The `qwen3_disable_thinking` renderer works by injecting an empty `<think>\n\n</think>\n\n` block into the observation *header* — the part that precedes the model's generation. It's a **signal** telling the model "don't think, just respond." It's the same mechanism as HuggingFace's `enable_thinking=False`.

But here's the critical detail: that signal lives in the header, which has weight=0 during training. The model learns from the actual response tokens, not the header. And during RL, as gradient updates accumulate and the model drifts further from its base weights, the signal gets weaker relative to the learned behavior.

This phenomenon — thinking tokens becoming uncontrolled during RL — is documented in the research literature. The GTR paper (ICCV 2025) calls it "thought collapse": thinking tokens receive no reward signal (rewards only come from `final_answer`), so they're unsupervised and can drift unpredictably.

### Why KL Didn't Save Us

In Run 6, `kl_penalty_coef=0.05` worked because we started from Run 5 step 10 — only 10 gradient updates from the base model. KL stayed between 0.04 and 0.38 throughout.

In Run 7, we started from Run 6 step 30 — already 40 gradient updates from base. By step 18, KL had risen to 0.75–1.30. The same penalty coefficient was insufficient to hold a model that was already further away.

**Lesson: KL penalty effectiveness depends on starting distance from base.** The further you are from the reference model, the harder KL has to work to hold the format.

| Run | Starting checkpoint | Steps from base | KL range | Collapsed? |
|-----|--------------------|-----------------|-|------------|
| Run 6 | Run 5 step 10 | ~10 | 0.04–0.38 | No |
| Run 7 | Run 6 step 30 | ~40 | 0.08–1.30 | Yes, step 13 |

The season-filter gap — the model's inability to write `WHERE m.season = X` Cypher — is still unsolved. We haven't been able to run long enough to know if RL alone can teach it.

## What's Next

The core problem is now clearer: the further we train from base, the harder it is to keep the model stable. We need a strategy that either:

1. **Keeps the model closer to base** — stronger KL, or restart from an earlier checkpoint
2. **Seeds the season-filter pattern before RL** — SFT on a handful of correct trajectories, so the model doesn't have to discover the pattern by exploration
3. **Suppresses thinking more robustly** — the `/no_think` soft switch in the system prompt, or switching to the Instruct variant of Qwen3 which has thinking more firmly post-trained away

The direction is still being decided.
